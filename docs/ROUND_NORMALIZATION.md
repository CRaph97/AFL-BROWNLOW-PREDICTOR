# Historical Round-Label Normalization (2023-2025 follow-up)

Status: **Resolved.** Follow-up to `docs/2026_ROUND_INTEGRITY_AUDIT.md`, which fixed the same
issue for 2026 and flagged 2023-2025 as needing a separate audit before any change (that audit
explicitly warned against assuming the 2026 pattern applies identically -- correctly, as this
audit found).

## 1. Per-season audit: the 2026 pattern does NOT apply uniformly

afltables' raw `Round` column was cross-checked against footywire's independently-sourced
`Round` column (`data/raw/fitzroy_data/player_stats.rda`), matched by calendar date, for every
round of every season 2021-2026:

| Season | afltables raw Round 1 | footywire's label for that week | Shift needed? |
|---|---|---|---|
| 2021 | 9 matches, 18 teams | "Round 1" | **No** -- no Opening Round concept existed |
| 2022 | 9 matches, 18 teams | "Round 1" | **No** -- no Opening Round concept existed |
| 2023 | 9 matches, 18 teams | "Round 1" | **No** -- 2023's Opening Round was itself labelled "Round 1" by both sources |
| 2024 | 4 matches, 8 teams (split) | "Round 0" | **Yes** -- raw N (N&ge;2) &rarr; official N-1 |
| 2025 | 4 matches, 8 teams (split) | "Round 0" | **Yes** -- same pattern as 2024 |
| 2026 | 5 matches, 10 teams (split) | "Round 0" | **Yes** (already fixed separately) |

This was verified by joining afltables' and footywire's round labels on match date for every
week of every season and diffing the label pairs directly (not assumed by analogy) -- see the
worked example already documented in `src/data/build_advanced_dataset.py`'s docstring (Adelaide
v Brisbane Lions, 2024-05-12: afltables "Round 10", footywire "Round 9") from the original Phase
2 investigation, which is the same root cause confirmed here at full-season scale.

**Conclusion: only 2024 and 2025 needed correction. 2023 was already correct and was left
untouched.** This directly disproves the assumption that "every season with an Opening Round
needs the 2026 fix" -- it does not.

## 2. Generalized normalization layer

`src/data/round_normalization.py` (new) is the single source of truth for both 2026 and
2023-2025:

```python
FIRST_SHIFTED_SEASON = 2024  # 2023 confirmed unaffected

def official_round(raw_round, season) -> int:
    if season < FIRST_SHIFTED_SEASON:
        return int(raw_round)
    return 0 if str(raw_round) == "1" else int(raw_round) - 1
```

`src/data/round_normalization_2026.py` is now a thin backward-compatible shim that binds these
same functions to `season=2026` -- no duplicated logic, and the 2026 fix's behaviour is
byte-for-byte unchanged (verified: `tests/test_2026_match_integrity.py`'s existing 2026
assertions still pass unmodified).

## 3. Where it was applied

`round` is descriptive metadata only. It is never used as a join key, sort-then-index key, or
model feature anywhere in `src/` or `dashboard/` (grep-audited; the only `round`-based
`.sort_values()` calls are display-ordering in `dashboard/data.py` and
`src/models/build_2026_outputs.py`, neither of which affects any prediction or metric).
Match identity remains `match_id`/`(season, date, home_team_id, away_team_id)` throughout --
untouched by this fix except for the round-embedded *substring* of `match_id`, which is
allowed and expected to change (see `docs/2026_ROUND_INTEGRITY_AUDIT.md`'s classification
scheme: this is a Class A, display/label-only issue, same as 2026).

Fixed at the earliest layer, then propagated to every file that carries a round value or a
round-embedded `match_id`:

- **`src/data/build_core_dataset.py`**: now computes `round_raw_source` (traceability) and the
  corrected `round` before constructing `match_id`. Rebuilt
  `data/processed/player_match_core_1984_2025.parquet` from raw source (full rerun of the
  Phase 2 canonical pipeline -- deterministic, target-integrity gate re-passed: all 7,413
  matches still have exactly one 3/2/1 vote-getter, summing to 6).
- **`src/data/build_advanced_dataset.py`**: unaffected code-wise (it already joins footywire
  stats onto CORE via `(date, team, opponent, surname)`, never round) but its output,
  `player_match_advanced_2010_2025.parquet`, was rebuilt because it inherits CORE's corrected
  `round`/`match_id` columns.
- **`data/processed/model_core.parquet`, `model_advanced.parquet`** (Phase 3/4 feature
  tables): rebuilt via `src/features/assemble_model_datasets.py` on top of the corrected CORE
  file.
- **Three downstream artifacts that key on `match_id` and cover 2024-2025** were found, during
  this audit, to be silently broken by the CORE rebuild until patched (see Section 4): they
  were **not** regenerated by rerunning their (expensive) source pipelines, but by a targeted,
  cheap `match_id`-string patch using the same `fix_match_id()` function -- no retraining, no
  re-fitting, no feature recomputation:
  - `data/processed/player_match_role_lagged.parquet` (19,044 rows patched: 9,522 each for
    2024/2025)
  - `data/processed/oos_predictions_core.parquet` (65,512 rows patched: 33,060 for 2024,
    32,452 for 2025)
  - `data/processed/experimental_gamestate_features.parquet` (18,222 rows patched: 9,040 for
    2024, 9,182 for 2025)

## 4. A real bug found mid-fix, and how it was resolved without retraining

Rebuilding `player_match_core_1984_2025.parquet` alone (with its `match_id` now correct)
initially caused `role`/`role_source` to silently become `NaN` for all 19,044 2024-2025 rows in
`model_core.parquet`/`model_advanced.parquet`. Root cause:
`src/features/assemble_model_datasets.py` merges a **separately pre-built** file,
`player_match_role_lagged.parquet`, onto the freshly-rebuilt CORE table using
`on=["match_id", "player_id"]` -- and that file still held the *old*, round-embedded
`match_id` values, so the join silently stopped matching for every 2024/2025 row the moment
CORE's `match_id` changed underneath it.

This is a genuine instance of exactly the risk this audit was told to look for -- `round`
(via its embedded presence in a `match_id` string) acting as an implicit part of a join key in
a place that wasn't the first one checked. It is **not** evidence that any model was trained on
round information: `build_role_lagged.py` sorts strictly by `(season, player_id, date)`, never
round, so the role classifications themselves were never wrong -- only the *label* used to
re-attach them to the corrected table went stale.

**Fix, not a rebuild**: `player_match_role_lagged.parquet`'s `match_id` column was patched with
`fix_match_id()` (a pure string rewrite, no model involved), and `model_core.parquet` /
`model_advanced.parquet` had only their `role`/`role_source` columns re-merged from the
corrected file -- a column-level patch, not a rerun of the ~14-minute
relative/context/teammate/composite/lagged-form feature pipeline. The same class of staleness
was checked for and found in two further files (`oos_predictions_core.parquet`,
`experimental_gamestate_features.parquet`), each fixed the same cheap way. No other
`match_id`-keyed file in the repository overlaps 2024-2025 with a still-stale `match_id`
(`role_reference_2021_2025.parquet` is keyed by `season, team_id, surname_key` -- no
`match_id`, unaffected).

## 6. What changed / what didn't

**Changed:** the `round` value and the round-embedded segment of `match_id`, for 2024 and 2025
rows only, in: `player_match_core_1984_2025.parquet`, `player_match_advanced_2010_2025.parquet`,
`model_core.parquet`, `model_advanced.parquet`, `player_match_role_lagged.parquet`,
`oos_predictions_core.parquet`, `experimental_gamestate_features.parquet`.

**Did not change:** 2023 or any earlier season (zero rows touched); any player statistic; any
model coefficient; any P(3)/P(2)/P(1)/expected-vote prediction; any Phase 4 backtest, ablation,
calibration, or season-level metric; the target-integrity guarantee (still exactly one 3/2/1
vote-getter per match, 7,413/7,413 matches); match identity (`season`, `date`, `home_team_id`,
`away_team_id` all untouched). No model was retrained.

## 7. Not actioned here

2021 and 2022 were checked as part of the per-season audit (Section 1) and confirmed to need no
change (no Opening Round concept existed). No further historical seasons remain flagged.
